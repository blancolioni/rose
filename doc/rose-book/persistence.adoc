= Persistence

The active state of the system is defined by the page object state, which is overridden by the swap state, which is overridden by the memory state.

== Checkpoint Objects

A page object is a single page (where the size of the page is architecture-dependent).
Object identifiers for page objects range from `ff00 0000 0000 0000` to `ffff ffff ffff ffff`.
A checkpoint state contains all page objects from a particular system state.

The swap state is a copy of the page object state, updated by page writes which have occurred since the last checkpoint.
A process addresses its own memory using normal virtual memory conventions; these hardware pages are mapped by the kernel to page object ids, which can index swap and page object state directly.

The memory state is a cache of the swap state.

== Checkpoint Operation

Persistence is implemented by a regular checkpoint operation.

[NOTE]
====
This section describes an earlier design, built on swap and change partitions.
Checkpoints are now written to a log by the log server, and the chapter is to be rewritten around it (#127).
====

=== Pages

Memory pages are always allocated read-only.
The first write to a page (if it is allowed) causes a page fault which switches the page to read/write and marks it as dirty.
When a dirty page is swapped out or synchronised, it is written to swap and its page object id is recorded in a list.

_Device pages_ are an exception.
A page that the kernel maps straight into a process, such as the VGA text page that `vga-console` writes to, is not managed by the memory server, so it is not part of a checkpoint.
The kernel marks such a page as a device page, in a spare bit of its page table entry, and leaves it writable while a checkpoint is active, so that a write to the screen during a checkpoint does not fault (ADR 0005).

=== Process

When a checkpoint begins, a new, empty, changed page object list is created.
All memory pages are marked as read-only, and all dirty pages are written to swap (via synchronisation).
The former changed page object list is scanned, and the changed pages are copied.
A new checkpoint is created, which references the previous checkpoint, the most recent checkpoint state, and page content copies.

If a page write occurs while the checkpoint process is running, a page fault will result (because all pages are read-only at this point).
If dirty pages are still being written, the faulting process will be blocked until the changed page object list scan starts.

=== Merge

From time to time, the most recent checkpoint is merged into a full page object state, which will be used for subsequent checkpoint operations.

There exists at least one consistent checkpoint state.
The last operation of a checkpoint merge writes an identifier which certifies the new checkpoint state.
When restoring a checkpoint, if this identifier is missing or malformed, the previous checkpoint state is used instead.

=== Pseudocode

==== Initialising Checkpoint

----
checkpoint:
   lock
      Checkpoint_State := Write_Dirty_Pages

      for Page of Writable_Page_List loop
         if Page.Dirty then
            Page.Write_To_Swap
         end if
         Page.Writable := False
      end loop
      Writable_Page_List.Clear
      old_list := current_list
      current_list := new Changed_Page_Object_List
      Checkpoint_State := Copy_Changed_Swap
   end lock
----

==== Copying Changed Blocks

----
for Page_Id of Changed_Page_Object_List loop
   Target_Block := Next_Changed_Page_Block
   Copy_Block (Active_Swap (Page_Id), Target_Block)
   Append_Checkpoint_Reference (Page_Id, Target_Block)
end loop
Commit_Checkpoint (Change_Page_Object_list)
----

==== Merging Checkpoint

----
Copy_Current_Page_Object_State
for Checkpoint of Incremental_Checkpoint_List
   for Page_Id of Checkpoint.Page_Id_List
      Copy_Block (Page_Id.Checkpoint_Block,
                  New_Page_Object_State.Block (Page_Id))
   end loop
end loop

Commit_And_Activate (New_page_Object_State)
----

== Restore

At boot, the `restore` server looks for a checkpoint: the last complete entry in the checkpoint log.
If it finds one, it brings back the persistent processes as they were at that checkpoint, in this order:

. the storage server's regions, through `Storage_Checkpoint`;
. each process in the kernel, with its capabilities, not yet runnable;
. each process in the memory server, with its segments, through `Memory_Restore`;
. the newest saved contents of each page the processes changed, from any log entry up to the checkpoint;
. the interrupts they handle.

When `init` has started the last boot modules and replied, `restore` resumes the processes (see <<restore-boot>>).
A restored process continues from where it was.
A process that was blocked in a system call makes the call again.

If there is no checkpoint, or it cannot be restored, `restore` starts a new log and installs the system instead.

[#restore-notification]
=== Telling a Process It Has Been Restored

Most processes need nothing more: everything they depend on was restored with them.
Some depend on state that a checkpoint cannot hold:

* *hardware*, since a reboot resets devices, so a driver's device is no longer set up the way the driver left it;
* *direct mappings*, such as the VGA text page, which the kernel maps straight into a process and which the memory server does not track, so the restored process no longer has it;
* *the screen*, which shows the messages of the boot that did the restore.

Such a process implements the `Restorable` interface (ADR 0004):

[source,ada]
----
interface Restorable is
   procedure Restored;
end Restorable;
----

* When `restore` resumes a process, the kernel looks for its `Restorable.Restored` endpoint.
  If it has one, the kernel sets the process's `Restore_Notice` flag.
* The next time the process receives, on any endpoint, the kernel clears the flag and sends it `Restored`, before any queued message or waiting sender.
  The message comes from the kernel, and has no reply cap.
* The notice comes once for each restore.
  If a checkpoint is taken while it is still pending, the flag is saved with the process, and a restore from that checkpoint sets it again.
* It does not make a blocked call safe: a process that was blocked in a call makes the call again first, and receives the notice at its next receive.

`vga-console` is the first process to use it: when it is told that it has been restored, it maps the VGA page again and redraws the screen as it was at the checkpoint (see <<Servers>>).

== Drive Layout

=== Partition Example

This is an example of how to partition a 64G disk.

[#disk-layout-64g]
.Example 64G disk layout
[cols="2,1,5",options="header"]
|===
| Partition | Size | Description
| Boot | 100MB | Grub, kernel image, boot modules
| Swap | 16G | Active swap partition
| State | 16G | Last checkpointed state
| Change | 16G | Changes since last full checkpoint
| Incremental | 12G | Changes since last incremental checkpoint
|===

=== Boot partition

This partition contains the boot sector, grub, a kernel image and enough modules to launch a minimal system.
The `restore` module looks for a checkpoint, and if it finds one, restores from it.
Otherwise, it installs the system (see <<Boot Sequence>>).

=== Swap and checkpoint state partition

These partitions are formatted identically.
Each block in the partition corresponds to exactly one page object; in particular, the block number or'd with the page object type specifier.

=== Change Partition

The change partition is divided into a header block, a range of change file blocks, and a range of changed page object blocks.

The change partition is cleared after a checkpoint merge.
