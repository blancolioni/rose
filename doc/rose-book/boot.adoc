= Boot Sequence

== Overview

Rose boots in one of two ways: from the install media, or from the boot disk, hd0.
In both, GRUB loads the kernel and the boot modules, and the kernel starts the first boot module, `init`, which starts the others in a fixed order.
The `restore` server then restores the system from its last checkpoint, if there is one.
`init` starts the checkpoint server, launches the shell if this boot installed a new system, and exits.

The two boots differ in their boot modules and in what they do when there is no checkpoint to restore (#373):

[#boot-variants]
.The two boots
[cols="1,3,3",options="header"]
|===
| | Install media | Boot disk
| GRUB menu | `images/iso/boot/grub/grub.cfg`, on the ISO | `images/hd0/grub.cfg`, on the boot partition, `rose-boot`
| Modules | 15: `init-install`, `restore-install`, `isofs`, and the 12 that both boots load | 14: `init`, `restore`, and the 12 that both boots load
| A checkpoint on hd0 | Restored | Restored
| No checkpoint on hd0 | A new system is installed from the install media, and GRUB is written to hd0 (see <<first-boot>>) | `init` says "no system on this disk; boot the install media", and the system stays idle
|===

The boot sequence is described in `src/servers/init/boot.yaml` (#374).
The build turns it into the Ada package `Init.Boot` with `scripts/make-init`, and writes the `module2` lines of both GRUB menus from it.
The boot description names each boot module, the object id it is launched with, its priority, the capabilities it is given and the endpoints `init` keeps from it.
The few steps that aren't wiring, such as launching the partition servers, are written by hand in `Init.Boot_Steps`.
What `init` does after the boot servers, installing a new system and launching the shell, is in `src/servers/init/src/init-run.adb`.

== The Kernel

GRUB loads the kernel with multiboot 2, together with the boot modules.
The kernel checks the modules against its own list for each boot, in `src/kernel/modules/rose-kernel-modules-init.adb`: the first module's name, `init-install` or `init`, says which list applies.
If they don't match, the kernel stops with a panic, because `init` launches boot modules by their position.

The kernel sets up the console, the memory map, its heap, the page table and the process table, then creates the `init` process.
The idle process has object id 1, and `init` has object id 2.
The kernel then switches its log output to the serial port and starts the clock.

`init` starts with a fixed set of 23 capabilities, at the indices given in `Rose.Init_Capabilities` (#115):

* the boot capability, for launching boot modules, and create-process, for `elf`;
* capabilities for creating endpoints, deleting and rescinding caps, and exiting;
* the memory map: reserving memory, counting and getting memory regions, and page-on;
* the clock: set-timeout and get-ticks;
* checkpoints and restore: enter and leave checkpoint, start-log, and restore-process, resume-process and restore-interrupt;
* trace events, and writing the system image;
* three _root capabilities_, for I/O ports, interrupts and device pages.

A root capability makes capabilities for hardware.
Given a range of ports, an interrupt vector or a physical page, it replies with a capability for just that, with less authority than its own; none of the capabilities it makes can make others.
The device-page root refuses a page that is RAM.

== `init`

`init` gives each program the hardware it needs from its root capabilities, through `Init.Grants`.
It records which program each port, interrupt and device page has gone to, and refuses it to any other.
A boot server is recorded by its object id, and an installed program by a number `init` gives it.
The boot console's screen and cursor ports are given to nobody, so they are not recorded, because the persistent console takes the screen over from the boot console (see <<handing-over-the-console>>).

Each boot module is launched with an object id, a priority, a capability for creating endpoints, and its own capabilities.
The launch replies with a copy capability for the new process, which `init` uses to copy the endpoints it needs from the module, such as the console's `Stream_Writer`.

An invocation is meant to carry at most four capabilities, and most modules need more, so they receive their capabilities in a cap set.
The cap set server, `caps`, is therefore the second module `init` starts.
The first two modules, `console` and `caps`, receive their capabilities directly in the launch invocation; every later module receives a single cap set, and reads its capabilities from it by index.

[NOTE]
====
The four-capability limit is not enforced yet: an invocation can carry up to 16 capabilities (`Max_Capabilities` in `Rose.Invocation`, #234).
====

== Boot Modules

Every boot server has a fixed object id (#372).
A process that holds a cap to a boot server holds its object id, so the id has to be the same on every boot, whichever boot it is and whichever modules it loads.

[#boot-modules]
.Boot servers, in the order `init` starts them
[cols="1,2,4,3",options="header"]
|===
| Id | Server | Receives | Provides to `init`
| 3 | `console` | The text buffer at `B8000`, as a device page; cursor ports `3D4` and `3D5` | `Stream_Writer` and `Output_Redirect`
| 14 | `caps` | The console | `Constructor`, for creating cap sets
| 4 | `mem` | Memory region queries, page-on, delete, trace | `Memory`, its `Checkpoint` endpoint, and `Memory_Restore`
| 13 | `timer` | The kernel's set-timeout and get-ticks | `Set_Timer`
| 5 | `pci` | PCI configuration ports `CF8` and `CFC` | Its device lookup endpoint
| 6 | `ata` | Ports `1F0`–`1F7` and `3F6`, IRQs 46 and 47, PCI, the timer | Block devices: hd0, the system disk, and on the install media hd1, the install media
| 7 | `store` | Delete, the console, trace | `Storage`, `Add_Backing_Store`, `Reserve_Storage` and `Storage_Checkpoint`
| 12 | `elf` | Create-process, `Memory`, delete, rescind, trace | `Executable.Launch` and `Launch_Command`
| 10 | `scan` | hd0 | `Partitions`
| 11 | `partition` | hd0, and the swap partition's start, bound and block size | The swap partition's `Block_Device`, with 4096-byte blocks
| 17 | `partition` | The same, for the log partition | The log partition's `Block_Device`, with 512-byte blocks
| 18 | `partition` | Install media only: hd0's block 0 | `Block_Device`, for writing the MBR
| 19 | `partition` | Install media only: the BIOS boot partition | `Block_Device`
| 20 | `partition` | Install media only: the boot partition | `Block_Device`, with 4096-byte blocks
| 8 | `isofs` | Install media only: hd1, delete | The install media's root directory
| 16 | `log` | The kernel's start-log capability | `Add_Log_Device`, `Append`, `Log_Reader`, and `Reset`
| 9 | `restore` or `restore-install` | The swap and log partitions, `Add_Backing_Store`, `init`'s install endpoint, the log's `Add_Log_Device` and `Log_Reader`, and the capabilities for restoring: the kernel's restore-process, resume-process and restore-interrupt, `Storage_Checkpoint` and `Memory_Restore`. `restore-install` also receives the install media, the log's `Reset`, and the three partition servers for the boot loader | (see <<restore-server>>)
| 15 | `checkpoint` | The timer, enter and leave checkpoint, delete, `Memory.Checkpoint`, log append, `Storage_Checkpoint` | --
|===

`init` launches the partition servers from the partitions that `scan` finds on hd0, using only the first of each type.
On a blank disk, `scan` first creates the partitions:

* `bios-boot`, 1 MiB, which holds GRUB's `core.img`;
* `rose-boot`, a 16 MiB EFI System Partition with a FAT file system, which holds GRUB's menu and modules, the kernel and the boot disk's boot modules;
* `rose-swap` and `rose-log`, which share the rest of the disk equally.

`checkpoint` is launched last, after `restore` has finished.

GRUB loads the modules in a different order, given by the `modules` list in `boot.yaml`: `init` first, then `console`, `mem`, `pci`, `ata`, `store`, `isofs` on the install media, `restore`, `scan`, `partition`, `elf`, `timer`, `caps`, `checkpoint` and `log`.
`partition` is loaded once, and launched once for each partition server.

[#restore-server]
== `restore`

Both `restore` servers start the same way:

. They add the log partition to `log`, so that the checkpoint log can be read.
. They look for a checkpoint: the last complete entry in the checkpoint log.
. They add the swap partition to `store` as backing storage, which both a restore and an install need.
. If there is a checkpoint, they restore it (see <<restore-boot>>).

What happens if there is no checkpoint, or it cannot be restored, depends on the boot:

* The boot disk's `restore` says "no system on this disk" and tells `init`, which stops (see <<boot-variants>>).
* The install media's `restore-install` installs a new system (see <<first-boot>>).

Either way, it finally tells `init` that it has finished, and whether it restored a checkpoint.

[#first-boot]
== First Boot

A new system is installed when the install media boots on a disk with no checkpoint.
`restore-install` starts a new checkpoint log, so that the entries of an old system are never mixed with the new one's.
It then reads the install media through `isofs`, and installs each program on it by sending it to `init`'s install endpoint:

* the drivers `exec`, `keyboard`, `vga-console` and `command`, which are launched;
* the file and directory servers `file` and `directory`, which are saved, and launched once for each file or directory;
* the commands `echo`, `list`, `cat`, `touch`, `mkdir`, `clear`, `user`, `auth`, `run_self_tests` and `petal`, which are saved in the command registry.

`init` serves the install endpoint while `restore-install` runs.
The first program installed is `exec`, which installs every later program.
The second is `keyboard`, which the console reads.
The third is `vga-console`, the persistent console and terminal (see <<Servers>>), and the fourth is `command`, the command registry, whose `Find` operation `init` keeps.
Once the console is running, `restore-install` sends `init` its input stream and its `Terminal`.

Each program on the install media comes with a list of the capabilities it asks for, such as `create-endpoint`, `register-interrupt 33` or `port-in-8 96`.
`init` grants each request that its policy allows, and leaves out the rest:

* any program may have `create-endpoint`;
* only drivers, the programs in the install media's `drivers` directory, may have the others: deleting and rescinding caps, interrupts, ports and device pages;
* hardware that another program already has is refused (see <<_init>>).

[#handing-over-the-console]
=== Handing over the console

Until `vga-console` is running, everything writes to the boot console, `console`, which is a boot module and not persistent.
When `restore-install` has launched `vga-console`, it sends `init` the new console's `Stream_Writer`, and `init`:

. tells the boot console to send everything it is given on to the new console, through `Output_Redirect`;
. tells `exec` to use the new console as the standard output of the programs it launches, and for its own output, through `Exec.Set_Standard_Output`;
. uses the new console itself, as the standard output of everything it installs or launches from then on.

The boot console passes its output on, rather than stopping, because boot modules and `restore-install` still hold caps to it.

[#writing-the-boot-loader]
=== Writing the boot loader

When the programs are installed, `restore-install` writes GRUB to hd0, so that the disk boots without the install media (#322).
The build makes three files for it with `scripts/make-boot-disk`, and puts them on the install media in `/rose/install/boot`:

[cols="1,2,4",options="header"]
|===
| File | Written to | Holds
| `boot.img` | hd0's block 0, the MBR | GRUB's first stage, which loads `core.img`. Only the boot code, the first 440 bytes, is written: the rest of the block holds the protective MBR's partition entry and signature, which the partition table needs.
| `core.img` | `bios-boot` | GRUB's second stage, which reads the boot partition
| `boot.fat` | `rose-boot` | The FAT file system: GRUB's menu, `images/hd0/grub.cfg`, its modules, the kernel and the boot disk's boot modules
|===

`restore-install` writes them through the install media's three extra partition servers.
A file that is missing, or doesn't fit its partition, is reported and left out.

The boot loader is written only when a new system is installed.
Updating the kernel and boot modules on a disk that already has a checkpoint is #375.

[#restore-boot]
== Restore Boot

Both boots restore the system if hd0 has a checkpoint, so booting the install media on an installed disk restores the system rather than installing it again.
`restore` brings back the persistent processes as they were at the checkpoint, in this order:

. the storage server's regions;
. each process in the kernel, not yet runnable;
. each process in the memory server, with its segments;
. the newest saved contents of each page they changed, from any log entry up to the checkpoint;
. the interrupts they handle.

The restored processes cannot run yet.
`init` starts `checkpoint`, then tells the boot console to discard its output, so that boot modules don't write over the restored screen.
It replies to `restore`, and exits without launching anything else: the programs it would launch are running already, as they were at the checkpoint.

When `init`'s reply arrives, `restore` resumes the restored processes.
A process that was blocked in a system call makes the call again when it runs, so most servers are back in a receive almost at once.
A process that depends on state a checkpoint cannot hold, such as a device or the screen, is told that it has been restored (see <<restore-notification>>).

== Starting the Shell

When a new system has been installed, `init` launches `checkpoint`.
It then runs the self tests, launches `auth`, creates the first user, `fraser`, with a home directory (ADR 0003), through `auth`, checks that `fraser` can log in, and launches `login`.

`login` is a command (#457).
Its roles give it the console, the system caps, the command registry and the timer, and its argument is `auth`.
It completes its launch call, so that `init` can go on, and then keeps running: it asks for a user name and a password at the console, and checks them with `auth`.
For the right password, it runs `petal`, which is also a command, with the console's streams, the system caps, the command registry, the console's `Terminal`, and the user, whose home directory is `petal`'s.
The call to `petal` returns when `petal` logs out, at the end of its input (#458), and `login` asks again.
For a wrong name or password, `login` waits three seconds, says `Login failed`, and asks again.

`init` then exits.

[NOTE]
====
The shell's caps are passed by position in a cap set.
ADR 0002 replaces this with roles, given in the launch invocation (see <<launch-sequence>>).
====

[#running-processes]
== Running Processes

These two diagrams show the processes that are running once each boot has finished, the processes that ran during the boot and exited, and which of them call which.
An arrow goes from a process to a process it holds a capability for and calls.

* *Persistent processes* have a rose border.
  They are in the checkpoint.
  An install boot installs them, and a restore brings them back.
* *Boot modules* have a black border.
  `init` starts them again on every boot, and each has its fixed object id (see <<boot-modules>>).
* *Dotted grey boxes*, between the two bands, are processes that ran during the boot and then exited.
  Their calls, made before they exited, and calls to them, are drawn in faint grey.
* *Dashed boxes and lines* are used only when booting from the install media.

[#processes-after-install]
.Processes after an install boot
image::processes-install.svg[Processes after an install boot,pdfwidth=100%]

After an install, `restore-install` has read the programs from `isofs`, sent them to `init` to install, and written the boot loader through partition servers 18 to 20 (see <<writing-the-boot-loader>>).
`init` has installed `exec` and the command registry through `store` and `elf`, created the first user through `auth`, and launched the self tests and `login` through `exec`.
`tests` has run its tests and exited.
The boot console sends its output on to `vga-console` (see <<handing-over-the-console>>).

[#processes-after-restore]
.Processes after restoring from the boot disk
image::processes-restore.svg[Processes after restoring from the boot disk,pdfwidth=100%]

After a restore, the persistent processes are the same, and their capabilities reach the new boot modules through the fixed object ids.
`isofs` and partition servers 18 to 20 are not started, `tests` is not run, and the boot console discards its output (see <<restore-boot>>).
`init` has only started the boot modules and read the partition table before `restore` told it that it had restored the system.

The diagrams leave out:

* output: every boot module writes to the boot console, and every installed program writes to `vga-console` through the standard output that `exec` gives it;
* paging: `mem` and `store` page the memory of every process;
* the swap and log partitions that `restore` holds, which it gives to `store` and `log`;
* `init` starting each boot module, which it does through the kernel;
* the commands that `petal` runs, and the processes that `tests` creates.

When it has finished, `restore` waits for a message that never comes, and keeps the capabilities it was given.
It should exit instead (#451).
