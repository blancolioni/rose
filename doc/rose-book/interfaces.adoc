= Interfaces

Every interface between Rose processes is declared in IDL (see <<idl>>), one interface to a file in `interfaces/`.
The file name is the interface name in lower case: `Cap_Set` is declared in `cap_set.idl`.

The build compiles 45 interfaces into Ada packages in `src/library/kernelapi/generated`, listed in that directory's `Makefile`.
`interfaces/` also holds the declarations that commands use: the package `Rose.Core` (see <<packages>>) and the standard stream roles `Standard_Input`, `Standard_Output`, `Standard_Error` and `Standard_IO` (see <<roles>>).
The build checks them with the interfaces, but generates nothing for them there; each command generates its own units.
`Data_Source` and `Rose_Interface` are declared but not compiled, and nothing uses them.

Each subprogram and each interface has an endpoint id derived from its declaration, so there is no table of ids to keep (see <<endpoint-ids>>).

In the tables below, _Parents_ are the interfaces an interface inherits, and _Implemented by_ names the server or driver that serves it, from `src/servers` or `src/drivers`.
An empty _Implemented by_ means that no server in the source serves that interface on its own; it may still be served as part of an interface that inherits it.

== Capabilities and Objects

[#capability-interfaces]
.Capability and object interfaces
[cols="2,2,4,2",options="header"]
|===
| Interface | Parents | Operations | Implemented by
| `Cap` | | `Destroy`, `Get_Object_Id` | `caps`, `timer`
| `Cap_Set` | | `Append`, `Get_Cap`, `Length` | `caps`
| `Constructor` | | `Create` | `caps`
| `Receiver` | | `Send_Cap` | `mem`
| `Named` | | `Name` |
| `Server` | | `Published_Interface` |
| `State` | | `Reset` | `log`
|===

A cap set holds a list of capabilities, so that a process can pass many capabilities as one:

[source,ada]
----
interface Cap_Set is

   procedure Append
     (Caps : Capability_Array);

   function Get_Cap
     (Index : Positive)
     return Capability;

   function Length
     return Natural;

end Cap_Set;
----

`Constructor` creates a new object and returns a capability for it; the `caps` server uses it to create cap sets.

== Processes and Memory

[#process-interfaces]
.Process and memory interfaces
[cols="2,2,4,2",options="header"]
|===
| Interface | Parents | Operations | Implemented by
| `Kernel_Process` | `Named`, `Cap` | `Resume`, `Fault`, `Notify` | The kernel
| `Process` | `Segment`, `Server`, `Cap` | `Heap_Interface`, `Exit_Process`, `Publish_Interface` | `mem`
| `Segment` | | `Add_Segment`, `Add_Nonpersistent_Segment` |
| `Heap` | | `Current_Bound`, `Request_New_Bound` | `mem`
| `Memory` | | `New_Process`, `Register_Process`, `Page_Fault`, `Take_Physical_Memory`, `Checkpoint` | `mem`
| `Region` | | `Get_Range`, `Get`, `Put`, `Read`, `Create_Subregion`, `Release` | `store`
| `Storage` | | `Reserve_Storage`, `Add_Backing_Store` | `store`
|===

`Memory.New_Process` takes the kernel's `Kernel_Process` capability for a new process and returns a `Process`, which describes the process's address space as segments:

[source,ada]
----
interface Process : Segment, Server, Cap is

   function Heap_Interface return interface Heap;

   procedure Exit_Process
     (Exit_Status : Natural);

   procedure Publish_Interface
     (Interface_Cap : Capability);

end Process;
----

A segment maps a range of virtual addresses onto a region of storage, with flags for `Segment_Readable`, `Segment_Writable`, `Segment_Executable`, `Segment_Resizable`, `Segment_Initialized` and `Segment_Private`.
A private segment's region belongs to its process, and is released when the process is gone.
A nonpersistent segment has no region behind it.

`Storage` reserves regions of persistent storage, backed by block devices, and a `Region` reads and writes its pages.
`Region.Release` frees a region that is no longer needed, with its storage if it has its own; neither the region nor its subregions can be used afterwards.

== Launching Programs

[#launch-interfaces]
.Interfaces for launching programs
[cols="2,2,4,2",options="header"]
|===
| Interface | Parents | Operations | Implemented by
| `Launch` | | `Launch`, `Launch_Command`, `Metadata` | `exec`
| `Exec` | `Launch` | `Install`, `Set_Standard_Output` | `exec`
| `Executable` | | `Launch`, `Launch_Command` | `elf`
| `Command_Endpoint` | | `Launch` | Each command
| `Map` | | `Add`, `Remove`, `Find` | `command`
|===

`Exec.Install` reads an executable from a stream and returns a `Launch` capability for it.
`Exec.Set_Standard_Output` sets the standard output that `exec` gives the programs it launches, and uses itself; `init` sets it to the persistent console once that is running.
`Executable.Launch` creates the process from an image in a region, and returns its `Process`.
`Map` holds launch capabilities by name.

A program is started in one of two ways:

* *`Launch.Launch`* takes a `Capability_Array` and an `Environment` storage array, whose meaning the caller and the program agree on by convention, and returns the new process's `Process`.
* *`Launch.Launch_Command`* starts the program as a command (ADR 0002, see <<launch-sequence>>).
  Its process starts with the receive capability of a command endpoint, and the result is the endpoint capability, which the shell calls once with the command's arguments.
  `Executable.Launch_Command` does the same for `elf`.

`Command_Endpoint` is that endpoint.
Its one operation, `Launch`, is only an endpoint id: the arguments are encoded as the command's own signature declares, and the command's generated main receives them through `Rose.Command_Line.Launch`.

`Launch.Metadata` returns a command's metadata, from the `.rose_command` section of its executable, or an empty string if the program is not a command.

== Streams and Files

[#stream-interfaces]
.Stream and file interfaces
[cols="2,2,4,2",options="header"]
|===
| Interface | Parents | Operations | Implemented by
| `Stream_Reader` | | `Read` | `isofs`, `store`, `vga-console`
| `Stream_Writer` | | `Write` | `console`, `vga-console`
| `Output_Redirect` | | `Redirect` | `console`
| `Stream` | `Stream_Reader`, `Stream_Writer` | |
| `Seekable` | | `Seek` |
| `File` | `Stream_Reader`, `Seekable` | `Size` |
| `Writable_File` | `File`, `Stream_Writer` | | `file`
| `Terminal` | `Stream` | `Enable_Echo`, `Disable_Echo` | `vga-console`
| `Directory` | | `Directory_Entry_Count`, `Directory_Entry_Name`, `Directory_Entry_Kind`, `Directory_Entry_Size`, `Find_Entry`, `Get_Ordinary_File`, `Get_Directory`, `Read_File` | `isofs`
| `Writable_Directory` | `Directory` | `Get_Writable_File`, `Get_Writable_Directory`, `Create_File`, `Create_Directory` | `directory`
| `File_System` | | `Root_Directory` | `isofs`
| `User` | `Named` | `Home_Directory` | `user`
| `Auth` | | `Login` | `auth`
| `Auth_Admin` | | `New_User` | `auth`
|===

`Output_Redirect.Redirect` sends everything written to a stream from then on to another `Stream_Writer`, or discards it if that is null.
The boot console implements it, so that its output can be handed over to the persistent console (see <<Boot Sequence>>).

A `User` gives the user's name, through `Named`, and the user's home directory, as a `Writable_Directory` (ADR 0003).

Files and directories come in a read-only and a writable form, so that the type of a capability says what right it grants (ADR 0002).
A `File` can be read and sought, and a `Writable_File` can also be written; a `Directory` can only be looked up, and a `Writable_Directory` can also create entries and return them in writable form.

A directory lists its entries by index, and gives a capability for each one:

[source,ada]
----
interface Directory is

   type File_Kind is (Directory, Ordinary_File, Special_File);

   function Directory_Entry_Count return Natural;
   function Directory_Entry_Name (Index : Positive) return String;
   function Directory_Entry_Kind (Index : Positive) return File_Kind;
   function Directory_Entry_Size (Index : Positive) return Storage_Count;

   function Find_Entry (Name : String) return Natural;

   function Get_Ordinary_File (Index : Positive) return interface File;
   function Get_Directory (Index : Positive) return interface Directory;

   function Read_File (Index : Positive) return interface Stream_Reader;

end Directory;
----

`Writable_Directory` adds the operations that need the right to modify it:

[source,ada]
----
interface Writable_Directory : Directory is

   function Get_Writable_File
     (Index : Positive) return interface Writable_File;
   function Get_Writable_Directory
     (Index : Positive) return interface Writable_Directory;

   function Create_File (Name : String) return interface Writable_File;
   function Create_Directory
     (Name : String) return interface Writable_Directory;

end Writable_Directory;
----

== Time and Logging

[#time-interfaces]
.Time and logging interfaces
[cols="2,2,4,2",options="header"]
|===
| Interface | Parents | Operations | Implemented by
| `Timer` | | `Set_Timer` | `timer`
| `Timeout` | | `On_Timeout` | `checkpoint`, `timer`
| `Kernel_Log` | | `Create`, `Append`, `Commit`, `Add_Log_Device` | `log`
| `Log_Reader` | | `First_Entry`, `Last_Entry`, `Next_Entry`, `Page_Count`, `Read_Page` | `log`
|===

`Timer.Set_Timer` invokes the capability it is given after a number of milliseconds, usually a `Timeout`, and returns a `Cap` whose `Destroy` cancels the timer.
The kernel notifies `Kernel_Log` as a checkpoint starts and commits.

`Log_Reader` reads the committed entries of the checkpoint log.
An entry is named by its location in the log, which never changes; `First_Entry`, `Last_Entry` and `Next_Entry` walk the entries, and `Read_Page` reads the pages of one.

== Checkpoints and Restore

[#restore-interfaces]
.Checkpoint and restore interfaces
[cols="2,2,4,2",options="header"]
|===
| Interface | Parents | Operations | Implemented by
| `Storage_Checkpoint` | | `Checkpoint`, `Restore_Region`, `Find_Region` | `store`
| `Memory_Restore` | | `Restore_Process`, `Restore_Segment`, `Restore_Zero_Segment`, `Restore_Page` | `mem`
| `Restorable` | | `Restored` | `vga-console`
|===

`Storage_Checkpoint` and `Memory_Restore` are the storage and memory servers' parts in checkpoints and restores.
They are kept out of `Storage` and `Memory`, so that only the checkpoint and restore servers, which `init` gives them to, can use them:

* `Storage_Checkpoint.Checkpoint` appends the storage server's region table to the checkpoint log, and `Restore_Region` recreates a region from it, with the index, pages and backing store space it had.
* `Memory_Restore` recreates the memory server's processes, with the ids they had, their segments, and the saved contents of their pages; a restored page is dirty, so the next checkpoint saves it again.

A process implements `Restorable` to be told that it has been restored.
The kernel, not another process, sends `Restored`, the first time the process receives after it is resumed (see <<restore-notification>>).

== Unused Interfaces

`Data_Source` (`Add_Sink`, `Remove_Sink`) and `Rose_Interface` (`Destroy`) are declared but not compiled, and nothing uses them.
