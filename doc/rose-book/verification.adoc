= Verification

Parts of Rose are written in SPARK, and proved with gnatprove: the proof shows that they raise no run-time errors, and that they keep the promises in their contracts.
`make prove` runs it, on the project `projects/spark.gpr`.

A package is in SPARK when it has `SPARK_Mode` on, in the package itself.
There is no configuration pragma, so the rest of Rose is compiled as before.
To bring a package into the proof, turn `SPARK_Mode` on in it and list its files in `Source_Files` in `projects/spark.gpr`.

Contracts are proved, not executed.
The run-time system has no assertions, so the build leaves them off.

`make prove` uses the userland run-time system.
Alire installs gnatprove in `~/.alire/bin`, which need not be on the path: `make prove GNATPROVE=~/.alire/bin/gnatprove` finds it.
It proves at level 1, which `PROVE_LEVEL` changes.

== Proved Packages

At level 1, with no unproved checks:

`Rose.Invocation`::
No run-time errors.
Sending a word or a capability, and sending an object id, require that the invocation has room: its counts of words and capabilities sent are modular, so without the precondition a seventeenth word would overwrite the first.
`Send_Word` and `Send_Cap` keep what was sent before.

`Rose.Capabilities.Layout`::
No run-time errors.

`Rose.Allocators`::
No run-time errors, for any sizes and addresses, in the instances with 4 and 19 bits of capacity (`Rose.Allocators_Proof`; the store uses 19, and gnatprove proves a generic through its instances).
`Allocate` and `Allocate_At` give a block that is aligned to its size and inside the allocator.
Not yet proved: that the block was free and no longer is, that live blocks do not overlap, that `Allocate_At` succeeds exactly when `Allocate` could have given that block, and that `Deallocate` frees exactly the block it is given.
The tree of free blocks used to keep a count for each level, which the proof would have needed an invariant for, and which only saved scans, so it is gone.

`Rose.Kernel.Command_Line`::
No run-time errors, for any command line from the boot loader: an empty argument, one that ends in `=`, one that starts with it, or one that does not fit.
The tables of names and values are always within the text that holds them, and `Get_Argument`, `Have_Argument` and `Argument_Count` agree.
`Integer_Argument` gives 0 for a value that overflows, as it does for one that is not a number.
The body that prints each argument and passes the adder to `Rose.Multiboot` is not in SPARK, so the contract of `Initialise_Command_Line` is assumed.

The kernel has its own run-time system, but `make prove` uses the userland one for `Rose.Kernel.Command_Line` too, since it uses nothing that they differ in.

`Rose.Command_Line.Items`::
No run-time errors in decoding an item of the launch buffer, for any contents and length of buffer: the buffer is from another process.
`Rose.Command_Line.Element` is the one conversion from the address of the buffer to an array, and calls it.
An item whose length is 2 ** 31 or more, which `Element` used to raise a constraint error for, is taken to be empty, as is one that does not fit in the buffer.
Not covered: `Natural_Argument`, which still raises a constraint error for a word of 2 ** 31 or more.

`Elf.Segments`::
What `elf` trusts of an executable's program headers.
No run-time errors, for any headers and any size of image, and `Describe` gives the segments to load only if each is inside the image, is not larger in the file than in memory, is not empty, ends below the stack without wrapping around, and does not overlap another.
`Elf.Format.Valid` also checks the class, data encoding, version and machine now, not only the magic number, and the loader reads no more than 64 program headers (an executable has about seven) and none from outside the image.
Not covered: the copy of a writable segment, which does not zero the rest of its last page (#265).

`Rose.Devices.GPT_Format`::
The format of a GUID partition table, apart from reading and writing it (`Rose.Devices.GPT` does that): the header and the partition entries as records, their layout in bytes, the CRC32, and what makes them valid.
No run-time errors, for any bytes and any disk.
The disk must be one that a GPT can be on (`Geometry_Valid`: a block size of 512 to 4096 that divides the pages the entries are read in, and room for the MBR, both headers and both copies of the entries).
A header is valid (`Header_Valid`) only if its signature, size, address and CRC are right, the entries are the standard size and there are at most 128, the entries are on the disk, and so is the range of blocks that partitions may use.
`Add` keeps a table valid: every partition is in the usable blocks, is not empty, and overlaps none, which is also what `Rose.Devices.GPT` checks of the entries that it reads, and of those that it is asked to add.
Not covered: the reading and writing of the blocks, and the table that is kept for each disk, which are in `Rose.Devices.GPT`.
